# LinkML gaps

This note records where the upstream LinkML generators (linkml 1.12) do not produce what the WoT Thing Description needs and what wot-toolchain does about it.
Differences between the generated artifacts and the published W3C artifacts are recorded in [`differences/`](differences/index.md).
It is meant for WoT WG members who review the generated artifacts and for LinkML maintainers who want to know which gaps are worth closing upstream.
How to change the schemas is described in the [authoring guide](../getting-started/first-change.md).

Each entry ends with one status word:

- Workaround: upstream LinkML does not produce what the TD needs, and the tool compensates.
- Shaping: the tool reshapes valid upstream output so that it has the shape of the published artifact.
- Undecided: the generated artifact differs from the published one, and no decision has been taken.

Where an upstream behaviour is pinned by a canary in `tests/test_upstream_canaries.py`, the canary is named; it fails once upstream changes, which is the signal to remove the workaround.
Module paths are relative to `src/wot_toolchain/`.

## JSON Schema

The JSON Schema is generated by the upstream `JsonSchemaGenerator` and then reshaped by the passes in `artifacts/jsonschema/postprocess.py`.

### Type designator crash

Upstream raises `ValueError: No such type: "Kind"` when a `designates_type` slot has an enum range.
On the TD schema, setting `designates_type` on `scheme`, whose range is the enum `SecuritySchemeList`, raises `No such type: "SecuritySchemeList"`.
`pipeline.py` clears `designates_type` on every slot while the JSON Schema is generated and restores it afterwards.
No current TD schema declares a `designates_type` slot, so the guard has nothing to clear today.
Canary: `test_jsonschema_crashes_on_enum_ranged_type_designator`.
Workaround.

### Discriminated unions

Upstream emits one definition per class and does not dispatch on a discriminator slot.
The TD security scheme is a `oneOf` over the known schemes plus an extension branch for other schemes.
The `jsonschema_oneof_dispatch` annotation (with `discriminator` and `include_unknown`) makes `build_oneof_dispatch` replace the class definition with a `oneOf` of its direct subclasses and, if requested, a catch-all branch whose discriminator matches `".+:.*"`.
That pattern is the one in the published schema; as an unanchored JSON Schema pattern it accepts any string with a colon after its first character, such as `ex:custom` or `https://a/b`, and rejects `:x` and strings without a colon.
Workaround.

### Form variants per affordance

Upstream emits a single `Form` definition.
The TD constrains `op` by location: a form on a property, action, event or the Thing itself accepts only the operation types valid there, so the published schema has one form definition per location.
The operation enum marks its values with `in_subset`, and the `jsonschema_enum_subset_partition` annotation on `Form` makes `build_enum_subset_partitions` emit a base definition plus one variant per subset, each with its own `op` schema.
The `jsonschema_form_subset` annotation in `slot_usage` then makes `narrow_form_subsets` point each affordance's `forms` at its variant.
Workaround.

### Subclass flattening

Upstream keeps subclasses as separate definitions.
Some TD structures are one JSON object with optional members in the published schema, not a choice between subtypes.
The `jsonschema_flatten_subclasses` annotation makes `_flatten_subclasses` merge subclass properties into the parent, delete the subclass definitions and carry the merged properties to classes that use the parent as a mixin.
Shaping.

### String maps

For the multi-language maps `titles` and `descriptions`, upstream emits `additionalProperties` as an `anyOf` of a reference to `MultiLanguage__identifier_optional` and `{"type": "string"}`.
The published schema allows only the string form.
`resolve_refs` replaces the `anyOf` with `{"type": "string"}`.
Workaround.

### Smaller rewrites

Several passes make the output match the published schema shape rather than fix a semantic gap.
For `title`, whose alternatives are `string` and `langString`, upstream emits `{"oneOf": [{"type": "string"}], "type": "string"}`; `dedup_oneof` and `normalize_types` reduce it to `{"type": "string"}`.
Upstream places a `type` next to many other `oneOf`s as well, and `normalize_types` removes most of them.
`remove_identifier_slots` removes identifier slots from object properties, since in the TD they are map keys, not members; upstream `PropertyAffordance` has a `name` property, the generated one does not.
`resolve_refs` inlines enum references as `{"type": "string", "enum": [...]}` and removes references to `linkml:Any`, so an unconstrained slot accepts any JSON value.
`remove_excluded_defs` drops classes marked `jsonschema_exclude`, the `__identifier_optional` helper definitions and the enum definitions.
`remove_unreferenced_candidate_defs` drops unreferenced abstract classes, the tree root, partitioned classes and classes standing in for `linkml:Any`.
`clean_metadata` drops `metamodel_version` and the `title` and `description` of every definition.
Shaping.

## JSON-LD context

The context is produced by the upstream `ContextGenerator` (with `fix_multivalue_containers`) and completed by the passes in `artifacts/jsonld_context/passes.py`.
The merged `context.jsonld` gets all the fixes below.
The per-module contexts built by `build_module_context` are flat, with no scoped contexts and no SKOS contexts.
They keep the `rdfs:Literal` coercion: `td-context` and `json-schema-context` on `title` and `description`, `wot-security-context` on `description`, and `hypermedia-context` on neither.

### Language maps

Upstream emits `titles` and `descriptions` with `@container: @index` and `@type: @id`.
These members are objects keyed by language tag, which JSON-LD reads as language-tagged strings only through a language map.
The `jsonld_container` annotation makes `_apply_root_mapping` set the container and remove the `@type` and `@index` that would conflict with it.
The root term in the merged context:

```json
"titles": {"@container": "@language", "@id": "titleInLanguage"}
```

Workaround.

### Index maps

Upstream emits `@container: @index` for TD maps such as `properties` and `securityDefinitions` but no `@index` property (JSON-LD 1.1 property-based indexing).
The generated context adds `@index` where the published context has it: `name` on the root `properties`, `actions`, `events` and `uriVariables`, and the `properties` terms inside scoped contexts.
It also adds `@index: propertyName` to `properties` in the scoped context of `uriVariables`, a term the published context does not declare there.
`securityDefinitions` and `schemaDefinitions` are not index maps in the generated context: the `jsonld_container: "@id"` annotation makes them id maps (`@container: @id`), so that each key becomes the IRI of the defined node and a `security` or `schema` name resolves to it. The published context declares both as index maps, `securityDefinitions` with `@index: hasInstanceConfiguration` and `schemaDefinitions` without `@index`.
pyld 3.3.0 does not expand the index key and drops it when converting to RDF, with the published context and with the generated one.
The `jsonld_index` annotation makes `_apply_root_mapping` add `@index`, `_ensure_index_term` declare the index term in the scoped context if it is missing, and `_apply_two_level_index_nesting` handle a map nested inside another map with a different index.
Upstream maps an identifier slot such as `name` to `@id`; for members of an index map `_fix_keyed_map_identifier_slots` maps it to its `slot_uri` instead, or removes it.
Workaround.

### Scoped contexts

Upstream defines a single `name` term at the root, mapped to `@id`.
In a TD the same key means different things by location.
`name` is `td:name` at the root of the generated context and `wotsec:name` in the `securityDefinitions` scope.
`_context_scope` chooses the scope of each slot, and a `jsonld_context` annotation overrides it; `schemaDefinitions` carries `jsonld_context: none`.
Workaround.

### Root terms

Upstream puts every slot of every merged module at the root of the context, including foreign terms such as `wotsec:in`.
A scoped definition overrides a root definition of the same key, so root terms do not hide scoped ones.
A foreign term at the root, however, applies wherever no scope redefines the key.
`remove_non_root_terms` keeps only terms in the default-prefix vocabulary plus the config file's `generators.jsonldcontext.extra_root_terms`, `remove_uninduced_slots` drops slots no class uses, and `remove_linkml_internals` drops the `linkml` prefix and terms.
With the generated context, an `in` member at Thing level expands to `td:in` through `@vocab`.
Shaping.

### Literal coercion

Upstream coerces a slot whose type maps to `rdfs:Literal` with `@type: rdfs:Literal`.
JSON-LD then gives every value the datatype IRI `rdfs:Literal`, for example `"Lamp"^^rdfs:Literal` for `title` with the per-module `td-context`.
`_remove_literal_type_coercion` removes the coercion in the merged context, so a plain string becomes a plain `xsd:string` literal.
Canary: `test_context_coerces_literal_typed_slot_to_rdfs_literal`.
Workaround.

### Enum values

Upstream gives an enum-ranged slot such as `op` a scoped SKOS context (`text` to `skos:notation`, `description` to `skos:prefLabel`, `meaning` to `@id`) and no coercion of its values.
In a TD, enum values such as `readproperty` are terms that expand to vocabulary IRIs (`td:readProperty`).
`strip_skos_enum_contexts` removes the SKOS context, `fix_enum_vocab_type_coercion` adds `@type: @vocab` (vocabulary-relative IRI expansion) when the values have a `meaning`, and `add_enum_value_aliases` adds a root term from each value to its meaning.

```json
"readproperty": "td:readProperty"
```

Canary: `test_context_emits_skos_context_for_enum_ranged_slot`.
Workaround.

### URI coercion

Upstream coerces `uri` and `uriorcurie` ranges to `xsd:anyURI`, for example on `anchor`, `href` and `unit`.
The published TD context maps `anchor` with `@type: @id`, maps `unit` with `@type: @vocab`, and keeps `xsd:anyURI` on `href` and `support`.
`fix_vocab_type_coercion` changes `uriorcurie` to `@vocab`.
`fix_object_property_id_coercion` coerces values with `@type: @id` for slots declared with `implements: [owl:ObjectProperty]`, such as `anchor` (range `uri`).
The generated context has the same coercions as the published context for these four terms.
Workaround.

### Spurious @id coercion

Upstream adds `@type: @id` in two cases where the TD needs a literal or a nested node.
A slot with range `Any` that implements `owl:DatatypeProperty` (canary `test_context_coerces_datatype_property_to_id`) is fixed by `strip_datatype_property_id_coercion`.
A slot whose range is an inlined class without an identifier (canary `test_context_coerces_inlined_class_without_identifier_to_id`) is fixed by `strip_inlined_class_id_coercion`.
Workaround.

### Type designator

Upstream does not map a `designates_type` slot to `@type`; it gives it a scoped SKOS context like any enum-ranged slot.
`fix_type_designator_mapping` maps such a slot to `{"@id": "@type"}` in scoped contexts and removes it from the root.
No current TD schema declares a `designates_type` slot, so the pass changes nothing today.
Upstream maps the slot that models the JSON key `@type` to `{"@id": "@type"}`; `remove_reserved_jsonld_slots` drops it, and JSON-LD still reads `"@type": "Thing"` as `rdf:type td:Thing`.
Workaround.

## SHACL

The shapes come from the upstream `ShaclGenerator` (closed shapes, `Shape` suffix) and pass through the passes in `artifacts/shacl/passes.py`.
SHACL is experimental.

### Literal datatype

Upstream emits `sh:datatype rdfs:Literal` for slots whose range type has the `uri` `rdfs:Literal`, which includes every `title` and `description` shape.
JSON-LD never produces a literal with the datatype IRI `rdfs:Literal` from a JSON string, number or boolean, or from a language-tagged string; it produces `xsd:string`, `xsd:integer`, `xsd:double`, `xsd:boolean` or `rdf:langString`.
pyshacl 0.40.2 nevertheless accepts all of these values against `sh:datatype rdfs:Literal`.
`sh:nodeKind sh:Literal`, which upstream also emits, accepts the same values.
The `remove_literal_datatype` pass removes the datatype.
Canary: `test_shacl_emits_rdfs_literal_datatype`.
Workaround.

### Language string alternatives

Upstream ignores an `exactly_one_of` over `string` and `langString` and takes `sh:datatype` from the `uri` of the slot's own range type, `rdfs:Literal` for `title`.
The `rewrite_langstring_union_to_sh_or` pass replaces that datatype with an `sh:or` over the distinct datatypes.
It reads only class `slot_usage`.
`rdf:langString` therefore occurs in exactly one place in the generated shapes, the `td:title` property shape of `td:ThingShape`.
The `exactly_one_of` on the `title` and `description` slots themselves is not rewritten, so all other `td:title` shapes and all `td:description` shapes carry only `sh:nodeKind sh:Literal`.

```turtle
sh:or ( [ sh:datatype xsd:string ] [ sh:datatype rdf:langString ] ) ;
```

Canary: `test_shacl_drops_langstring_branch_of_exactly_one_of`.
LinkML discussion #2199.
Workaround.

### JSON-LD keywords

Upstream emits property shapes with paths such as `td:atType` and `wotsec:atType` for the slots that model `@context` and `@type`.
JSON-LD reads `@context` as no triple at all and `@type` as `rdf:type`, so these paths never occur in TD data.
The `remove_jsonld_keyword_properties` pass removes those property shapes.
Every closed shape lists `rdf:type` in `sh:ignoredProperties`, so `rdf:type` triples pass the closed check.
Shaping.

## OWL

The ontologies are generated per module by the upstream `OwlSchemaGenerator` through a subclass, a schema preprocessor and graph passes.
OWL is experimental.

### Annotation IRIs

Upstream emits every value of a CURIE-keyed annotation as a literal, so `rdfs:subPropertyOf: dcterms:title` becomes the literal `"dcterms:title"`.
The schemas use such annotations for `rdfs:subPropertyOf`, `rdfs:subClassOf` and `rdfs:seeAlso`, whose values have to be IRIs for the axiom to mean anything.
The generated ontology has `td:title rdfs:subPropertyOf dcterms:title` with an IRI object.
Canaries: `test_owl_emits_subproperty_annotation_as_literal_curie`, `test_owl_emits_uri_annotation_as_literal`.
Workaround.

### Multiple domains

Upstream gives a slot without a single `domain` no domain at all, so `td:title`, which `Thing`, `InteractionAffordance` and `DataSchema` use, gets none.
A graph pass adds one `schema:domainIncludes` triple per class for properties used by several classes.
How this compares with the published ontologies is under "Single-class includes replaced by rdfs:domain and rdfs:range" in [OWL differences](differences/owl.md#single-class-includes-replaced-by-rdfsdomain-and-rdfsrange).
Workaround.

### Attribute ranges

Upstream gives `td:name`, a class attribute of `InteractionAffordance` with range `string`, neither `rdfs:range` nor `rdfs:domain`.
The generated ontology gives it `rdfs:range xsd:string` and `rdfs:domain td:InteractionAffordance`.
Workaround.

### Restrictions

Upstream turns slot constraints into `owl:Restriction` axioms, also with the tool's generator options.
The published TD ontologies and the generated ones carry no restrictions.
Shaping.

### Enum values

With default options upstream emits each permissible value of `OperationType`, such as `td:readProperty`, as an `owl:Class` that is both an instance and a subclass of `td:OperationType`, and covers the enum with `owl:unionOf`.
With the tool's options the values are subclasses only, and the covering axiom remains.
In the published and the generated ontologies each value is only an instance of `td:OperationType`, with no covering axiom.
Shaping.

### Module scope

Upstream emits subjects from every vocabulary the schema uses, including `linkml`, `hctl`, `jsonschema` and `wotsec` terms in the TD ontology.
The generated TD ontology has subjects only in the `td` namespace and the ontology IRI.
Shaping.

### Schema objects

After the OWL preprocessor passes have run on a `SchemaDefinition`, upstream fails on that object with `AttributeError: 'JsonObj' object has no attribute 'values'`.
The same object before the passes, and the YAML serialization of the object after them, generate without error.
The tool passes the YAML serialization.
Workaround.

## LinkML modelling gaps

Several workarounds above are driven by schema annotations, because the LinkML metamodel cannot state the requirement.
What each annotation is for, and what would let it go, is listed in [WoT custom annotations](../reference/annotations.md#when-an-annotation-can-go).
The semantics that LinkML can express are written with native metaslots: `implements: [owl:ObjectProperty]` or `[owl:DatatypeProperty]`, `identifier`, `inlined`, `designates_type` and `meaning` on permissible values.

### JSON-LD containers and indexes

The metamodel has no slot for a JSON-LD container kind or an index property.
`jsonld_container` and `jsonld_index` fill that gap.
A native slot-level setting would remove both annotations.
Workaround.

### Location-dependent terms

The metamodel can give a slot an `alias` and a `slot_uri`, but not different ones per containing class: upstream rejects an `alias` in `slot_usage`, and the upstream context generator ignores a `slot_uri` set there.
`jsonld_context` sets the scope explicitly where `_context_scope` cannot choose it.
Workaround.

### Discriminated unions

`designates_type` describes a type designator, but it has no way to state an open extension branch, and the upstream JSON Schema generator crashes on the enum-ranged `scheme` (see "Type designator crash").
`jsonschema_oneof_dispatch` states the discriminator and whether unknown values are allowed.
Workaround.

### Enum subsets per location

`in_subset` can mark permissible values, but nothing connects a subset to the classes where only that subset is valid.
`jsonschema_enum_subset_partition` and `jsonschema_form_subset` make that link for forms.
Workaround.

### Scalar unions with language strings

`exactly_one_of` over `string` and `langString` is valid LinkML.
Upstream SHACL takes the datatype from the slot's own range and upstream JSON Schema reduces the alternatives to a one-branch `oneOf` of `string`.
In the generated shapes `rdf:langString` occurs only in the `td:title` shape of `td:ThingShape`, and the merged context gives `title` and `description` no coercion.
See LinkML discussions #2199 and #2896 and linkml-model PR #276.
Workaround.

### Multiple domains

`domain` takes a single class, while TD properties are shared across classes.
The OWL output derives the classes from the slots each class uses.
Workaround.
